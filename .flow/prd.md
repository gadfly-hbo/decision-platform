# PRD · 决策看板 M1（结论→证据→行动 看板雏形）

> 事实源：`.flow/proposal.md`（用户已决项）；本文对齐红队报告 `.flow/red-team.md`。
> 发布说明：项目未配置 issue tracker，PRD 落盘 `.flow/prd.md`（降级路径）。

## Problem Statement

决策者每天面对的是"发生了什么"的数据图表（BI 看板/Excel 周报），但从看到数据到做出决定之间的路径（找原因、判断严重度、想对策）全靠人脑完成。用户需要一个打开就知道"今天要拍板什么"的决策看板：结论先行、证据可展开核查、行动可直接采纳。

## Solution

一个单页决策看板：顶部是按紧急度排序的结论列表（一句话说清什么指标、偏离多少、大概什么原因）；点开任一结论，展开该结论的完整推导过程（分析链路步骤 + 核心指标趋势图 + 归因明细表）与建议行动；行动可标记采纳状态。M1 用演示数据（线上经营·渠道投放域）跑通完整形态，数据全部来自一个类型化数据模块，未来接真实数据源只换数据、不改界面。

## User Stories

1. 作为运营决策者，我打开看板先看到今天需要拍板的结论列表（按严重度排序），以便 30 秒内知道要处理什么。
2. 作为运营决策者，我想每条结论用一句话说清"什么指标、偏离多少、大概什么原因"，以便不点开也能扫读全局。
3. 作为运营决策者，我想通过严重度标识（高/中/低）快速区分结论的紧急程度，以便先处理最要紧的。
4. 作为运营决策者，我想点开结论卡看到推导这个结论的分析过程（逐步链路：检测到什么→归因到哪→匹配了什么规则），以便判断结论是否可信。
5. 作为运营决策者，我想在展开区看到核心指标的趋势图表（含对比基准或阈值线），以便肉眼复核异动是否真实。
6. 作为运营决策者，我想在展开区看到归因明细表（哪个渠道/计划贡献了多少偏离，按贡献排序），以便定位到责任单元。
7. 作为运营决策者，我想看到每条结论的建议行动（一句话动作 + 预期影响），以便直接拍板而不是自己想对策。
8. 作为运营决策者，我想把建议行动标记为 待定/采纳/驳回，以便在行动汇总区追踪今天做了哪些决定。
9. 作为运营决策者，我想看到结论的数据窗口与更新时间，以便判断结论的时效性。
10. 作为看板维护者，我想全部数据（结论、推导链、指标、归因、行动）来自单一类型化数据模块，以便接真实数据源时只替换数据层。
11. 作为看板维护者，我想指标（名称、单位、口径说明、格式化）在数据层定义一次、全局引用，以便各处口径一致（指标层原则的最小落地）。
12. 作为看板维护者，我想数据接口能同时承载两种不同业务域的假想数据（渠道投放 + 电商经营映射走查），以便避免接口只贴合单一演示场景（红队 KA3 缓解）。
13. 作为首次观看者，我想看板顶部有一句"这是什么、怎么看"的说明，以便无引导也能上手。
14. 作为用户，我想看板在数据缺失时有明确的空状态说明（接口预留），以便不面对白板或误把占位当真实。
15. 作为用户，我想状态永远用"颜色 + 文字"双通道表达、视觉遵循统一设计语言（Xanthil 暖灰青），以便语义清晰、界面一致。
16. 作为用户，在窄屏下我仍能纵向可用地浏览看板（响应式降级），以便在笔记本半屏使用。

## Implementation Decisions

- **单页三区信息架构**：概览头（产品句、数据窗口、更新时间）→ 结论区（决策卡列表，严重度高→低排序）→ 行动汇总区（全部建议动作与状态）。证据区不做独立页，而是结论卡的展开态。
- **结论卡展开态四块结构**：① 推导链路（有序步骤，演示数据按"检测→归因→规则匹配→建议"构造）；② 核心指标图（ECharts 折线 + 基准/阈值标线）；③ 归因明细表（按偏离贡献排序）；④ 建议行动（动作 + 预期影响 + 状态标记）。
- **严重度三级**：高/中/低，对应语义色对（fail/warn/queue 系），chip 必须"色 + 文字"双通道。
- **数据层契约**：单一数据模块导出类型化对象——结论（id、严重度、标题句、摘要、数据窗口、推导步骤、指标引用、归因明细、建议行动）、指标定义（id、名称、单位、口径说明、格式化）、指标序列（时间序列点 + 基准线）。UI 只消费类型，不出现内联业务数据。
- **指标定义集中**：名称/单位/口径在数据层定义一次；展示层按指标 id 引用（指标层"定义一次、全局一致"原则的 M1 最小落地）。
- **图表**：ECharts 按需引入，薄封装（初始化、更新、销毁、resize），不引入图表封装库。
- **样式**：原生 CSS 变量承载 Xanthil token（色彩/字体/圆角/间距），自定义控件，不引入组件库与 CSS 框架；采用规范的卡片/chip/表格/空状态语义，**不实现**三栏工作台外壳（侧栏/Inspector/阶段条）——M1 是看板单页，工作台形态留给产品化阶段。
- **状态管理**：仅"结论展开/收起"与"行动状态"两个 UI 态，React 内置 state，不引入状态库；行动状态仅内存态不持久化。
- **演示场景定案**：线上经营·渠道投放（ROI 预算决策域）；4 条结论覆盖高/中/低三级严重度；指标窗口 14 天；归因维度到"渠道/计划"两级。

## Testing Decisions

- 好测试只测外部行为：渲染给定数据后，断言用户可见的结果——结论排序、严重度标识、展开交互后的四块结构、行动状态切换；不断言组件内部实现细节。
- **Seam（唯一测试缝，最高可用层）：数据模块边界。** 全部测试通过渲染 App 外壳并使用/替换数据模块进行，UI 不为测试开低层缝。
- 工具：Vitest + @testing-library/react + jsdom。
- 先例：新仓库无先例，本 flow 建立项目测试范式。
- ECharts 在测试中 stub 渲染：断言图表容器的存在与传入 option 的关键结构（序列、标线），不依赖 canvas。

## Out of Scope

- 真实数据源接入、后端服务、DuckDB、真实指标计算（M2+）。
- 异动检测与自动归因算法（M2）——M1 的推导链路是演示数据预先构造的静态内容。
- 告警推送、行动指派负责人、持久化、闭环追踪（M3）。
- 权限、多用户、部署形态、暗色主题（规范未定义）。
- Xanthil 三栏工作台外壳（命令面板、Inspector、状态栏）。

## Further Notes

- **M2 前置门（红队 KA1）**：启动 M2 前应拿到一份真实数据源样本 + 一个试用承诺，否则 M2 方向存疑。
- 类型设计需通过"双域映射走查"（渠道投放数据 + 电商经营假想数据）才算完成（任务拆解中体现）。
- 30 秒验收标准在 M1 只能以形态满足（演示数据预先构造了值得拍板的结论），真实信噪比验证属于 M2。

## GRILL 决议（自答记录，2026-09-25）

1. **包管理与脚手架**：npm（本机 node v25，无 pnpm）；Vite react-ts 手工脚手架（目录非空避免交互式 create）；不引入 CSS/组件库（PRD 已决）。

4. **结论展开默认态**：默认展开第一条（最高严重度），其余收起，可多开——兼顾"先扫读全局"与"首屏即见核心交互"。
5. **行动状态事实源**：状态提升到应用层、按行动 id 索引；结论卡与行动汇总区共享同一状态（单一事实源）。
6. **响应式断点**：≤900px 单列纵向堆叠（对齐 Xanthil 规范的堆叠断点）。
7. **git 仓库**：IMPLEMENT 首次进入前 git init + .gitignore（node_modules/dist/.flow/state.json）+ 基线提交（.flow durable artifacts），使 REVIEW 两轴审查有 review_base 起点。dev-flow 流程本身授权提交。
8. **verify 命令定案**：`npm run verify` = `tsc --noEmit && vitest run && vite build`（类型/测试/构建三重门，一条命令）。

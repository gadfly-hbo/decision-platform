# Red-Team: M3 告警推送、行动闭环、多周趋势

评估对象：`.flow/proposal.md`（M3 全文）。时间：2026-09-26。

## Top Kill-Assumptions（按 影响 × 可能性 × 测试成本 排序）

### KA1. 「行动闭环的"闭"有人维护」
- **Claim:** 用户每周会在看板上把行动推进到"已执行"并写备注，跨周对照因此有意义。
- **Fails if:** 行动标记停留在"采纳"不再更新——闭环变形式，跨周对照展示的是过时状态（比没有更糟，因为它假装闭环了）。
- **Evidence to get this week:** 第一个真实周期（下周一）行动是否被推进到已执行。
- **Kill criterion:** 连续 4 周行动标记率（有终态/总采纳）<50% → 简化为只记采纳/驳回，砍掉已执行与跨周对照。
- **Cheapest test:** 本周用一次：周一推送 → 周三前标记 → 下周看对照是否成立。

### KA2. 「推送的摘要有人看且促发动作」
- **Claim:** 每周一条决策摘要推送（webhook）会被打开并促使看板被打开。
- **Fails if:** 推送淹没在群消息里无人响应——推送疲劳；或摘要写成数据通报（"零售额 X 万同比 Y%"）而非"本周要拍板的 3 件事"，价值归零。
- **Evidence to get this week:** 首次真实推送后的响应（是否有人打开看板/回复）。
- **Kill criterion:** 连续 3 周推送无任何响应 → 降级为周会现场手动打开，砍自动推送。
- **Cheapest test:** 摘要模板先写"结论 + 待拍板动作数"，发给自己一周验证打开行为。

### KA3. 「多周趋势有数据可攒」
- **Claim:** data/raw 会随周报累积 ≥4 期，趋势图与未来的趋势规则有料。
- **Fails if:** 导入节奏断更（M2 红队 KA1 的延续风险）——趋势功能上线即空转，降级提示长期显示。
- **Evidence:** 每周一观察 data/raw 期数。
- **Kill criterion:** 6 周内 <3 期 → 导入自动化提上日程（定时拉取或导出提醒）。
- **缓解已在提案：** <2 期降级 + 不做无数据校准的趋势规则。

### KA4. 「webhook 凭证管理可接受」
- **Claim:** data/notify.json（gitignore）单机配置足够。
- **Fails if:** 双机使用时 MacBook 忘配凭证 → 自动推送静默跳过，用户以为推了（需日志/看板明示"推送未配置"状态而非静默）。
- **Kill criterion:** 出现一次"以为推了其实没推"的事故 → 推送状态上看板（概览头小标）。
- **Cheapest test:** 看板概览头显示推送配置状态（未配置/已配置/最近推送期次）——低成本高确定性的防御，建议直接做进 M3。

## What's Well-Reasoned

- **推送幂等设计**（新期次首次计算后推一次）：避免重复刷新重推，这是推送类功能最常见的自伤点。
- **趋势规则不本期做**：M2 用血泪验证了"规则参数必须真实样本校准"，1 期数据攒不出阈值——克制正确。
- **行动持久化用 JSON 文件**：单人小团队、无并发，引数据库是过度设计。
- **打磨项捎带修复**：三项都是审查确认的小修，随 flow 走审查比攒着强。

## What I Couldn't Assess

- 推送目标群/人的实际消息环境（飞书/钉钉/企微哪家、群里消息密度）——影响摘要文案长度设计。
- 「已执行」的实际业务语义（执行=预算调整已提交？活动已上线？）——影响备注字段设计，GRILL 需自答一个宽松默认。

## Verdict: **GO**

三大件都有 M2 打下的真实地基（结论引擎、数据管道、看板形态），最大风险是运营性（KA1/KA2 靠纪律与文案），工程风险低。KA4 的防御（推送状态上板）建议纳入范围。

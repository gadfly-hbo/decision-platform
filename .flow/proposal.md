# decision-platform · 决策看板 — 提案（讨论稿定稿）

> 来源：2026-09-25 会话讨论。本文件是后续 PRD / 拷问 / 拆解 / 审查的事实源。

## 产品定位

- 项目从数据分析延伸到**决策看板**，整个产品围绕决策看板展开，而非纯数据展示。
- 核心区分：BI 看板回答"发生了什么"，决策看板回答"现在该做什么"。
- **验收标准（用户认同）**：打开看板 30 秒内，用户能说出今天要拍板的一件事；达不到就还是数据看板。每个功能迭代都用这条标准检验。

## 看板形态（用户明确认同，核心结构）

信息层次自上而下：

1. **结论区**：今天有哪些指标需要决策（异动、逼近阈值、目标偏差），按紧急度排序，一句话说清"什么指标、偏离多少、大概什么原因"。
   - **结论可展开**：展开后能看到**推导这个结论的数据分析过程**（推导链路）及**核心指标数据**（用户明确要求的重点）。
2. **证据区**：点开结论后是传统图表——趋势、同环比、下钻归因（哪个渠道/地区/品类导致异动）。
3. **行动区**：基于规则或分析给出建议动作，可指派负责人、追踪后续结果，形成闭环。

## 架构原则

- **指标层是核心资产**：指标定义一次、全局口径一致；看板只引用指标，不自定义 SQL。M1 用演示数据体现该结构（类型化数据接口），后续接真实数据源。
- 数据质量原则：接入即校验（缺失、延迟、异常值）——M1 暂不实现，作为架构预留。

## 节奏（用户明确：先从看板做起，逐步完善）

- **M1（本次 flow 范围）**：看板雏形——结论→证据→行动三区 + 结论可展开（推导过程 + 核心指标图表 + 归因明细）+ 演示数据。纯前端。
- M2（后续）：异动检测（简单规则：环比/同比偏离阈值）+ 下钻归因。
- M3（后续）：告警推送 + 行动建议 + 闭环追踪。
- 一个场景跑通闭环 > 十个半成品场景；抽象等有两个以上真实场景再做。

## 技术栈（会话中推荐，用户以"先从看板做起"默认接受）

- 前端：React + Vite + TypeScript；图表 ECharts；表格先用原生/轻量实现。
- 后端（M2+ 再引入）：Node（Hono 或 NestJS）+ DuckDB 嵌入式分析引擎。
- 自建轻量版 vs 基于开源 BI 扩展：MVP 自建轻量版。
- UI：遵循全局 Xanthil 暖灰青工作台设计规范（~/.zcode/design/DESIGN.md，token 已读取）。项目无自己的 DESIGN.md，全局规范即默认视觉基线。

- 技术栈 React+Vite+TS+ECharts。

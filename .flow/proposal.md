# 提案：M8 — 抽取输出容错修复（runText + 宿主解析 + 数量上限 + 修复重试）

日期：2026-10-13。来源：用户真实报告两次抽取失败（诊断对话），修复方案用户逐字确认「按 1+2（+3）走一轮 dev-flow 修掉」。

## 诊断结论（锚点）

真实报告《国内电商平台流量趋势与公私域打法研究报告》两次抽取均 `INVALID_OUTPUT`：模型调用与计费正常（MiniMax-M3，各 ~65s，input 15966 / output ~10800 tokens），失败在 SDK `runWorker` 对回复文本的严格 `JSON.parse`——大报告输出带围栏/说明文字/截断即整轮失败。

## 已确认决策（用户三点）

1. **抽取入口 runWorker → runText + 宿主自解析**：剥围栏 → 字符串感知的数组段提取 → 宽松修复（注释/尾逗号）→ 既有 `validateActionDrafts` 归一化（结构/枚举/置信度校验不放松）；容错对齐 pi-xanthil 三级前两级。
2. **prompt 增加行动项数量上限（≤6 条，取优先级最高）**：防长报告输出顶到 8192 token 截断线。
3. **解析仍失败 → 自动带修复提示重试一次**（同 taskId 新 run，账本正常累计；再失败才落 failed）。

## 约束

- 合规：SDK 标准 P2 允许宿主自定义校验路径（runText 文本入口）；结构化校验仍由宿主完成。
- 行为面：`runExtraction` 对外签名与返回不变；失败语义（报告 failed + error 文案）不变。
- 无 UI 变更（S1b 失败态已存在）；无 schema/存储变更。

# M4 产品方案：移动审批 · IM 集成（proposal）

- 状态：**已定稿 v1.1，可进 `/dev-flow` M4**（决策记录见 §9）
- 日期：2026-09-27
- 前置：M1 看板形态 / M2 真实数据异动检测+归因 / M3 告警推送+行动闭环+多周趋势（均已交付）

## 1. 背景与目标

现状：PC 看板（结论→证据→行动三区）+ 真实周报异动检测与归因 + 群机器人纯文本周摘要推送（飞书/钉钉/企微/generic）+ 行动四态闭环（待定/采纳/驳回/已执行，`data/actions.json` 持久化）。

问题：推送已经到手机了，但「拍板」仍必须回 PC——决策人在通勤路上收到「高优先级 N 条待拍板」，只能记下来回办公室再操作。

**目标**：让决策人在常用的 IM App 内完成候选决策审批——查看结论与关键证据 → 采纳/驳回——全程不离开 IM、不装新 App。

**验收北极星**：从收到推送到完成一条候选决策审批 ≤ 30 秒（呼应 M1 的「打开 30 秒说出要拍板什么」）。

**非目标**（首期明确不做）：

- 不做独立 App、不上架应用市场
- 不做全功能移动看板（PC 仍是主工作台）
- 不做多租户 SaaS
- 不做企业微信、个人微信（公众号/小程序）——已排除，见 §4

## 2. 核心用户与场景

- **决策人（拍板者，移动端主要用户）**：碎片时间收到周报摘要 → 每条高优结论一张卡片：标题 + 关键数字 + 一句话归因 → 点【采纳】/【驳回】→ 卡片即时变为结果态（谁、何时、怎么批的）。
- **运营/分析（PC 端用户，行为不变）**：导周报、核查证据链、标记已执行+备注。

## 3. 现状盘点 → 差距

已有（可直接复用）：

- **审批的数据模型与 API 已存在**：`PUT /api/actions/:id`（status 四态校验、备注、原子写）。移动审批本质是把这条 API 的触达延伸到 IM，不是新建审批系统。
- **平台适配雏形已有**：`server/notify.ts` 已按 feishu/dingtalk 做 payload 差异适配——但走的是「群自定义机器人 webhook」，纯文本、**单向**、收不了回调。
- **行动 id 跨期稳定**（M3 已做）：卡片引用行动 id 是可靠的。

差距（按依赖排序）：

1. 无用户/鉴权体系；服务仅监听 `127.0.0.1` 且写操作无鉴权——但**档 1 内网部署下服务不出公网**，该问题收窄为内网边界管理（见 §6）。
2. 无「应用级」IM 集成：收卡片按钮回调必须建**自建应用**（飞书/钉钉开放平台），群机器人 webhook 做不到。
3. 审批留痕缺失：`ActionRecord` 无 decidedBy / decidedVia。
4. 双机独立运行模式（Mac mini / MacBook 各自 `actions.json`）与「回调要求单实例常驻」冲突。

## 4. 平台范围（已决策：飞书 + 钉钉）

| 能力 | 飞书 | 钉钉 |
|---|---|---|
| 卡片按钮审批（IM 内直审） | ✅ 交互卡片 | ✅ ActionCard/酷应用卡片 |
| 接收回调 | 长连接 WebSocket，**免公网** | Stream 模式 WebSocket，**免公网**（个别卡片场景需 HTTP，见 §8） |
| IM 内 H5 免登 | ✅ 网页应用 OAuth（**要求公网 HTTPS 域名**，档 1 下不可用） | ✅ H5 微应用免登（同左） |
| 原生审批中心对接 | ✅ 审批 API（M5+ 候选） | ✅ OA 审批（M5+ 候选） |
| 前置条件 | 企业自建应用，企业后台直接创建，无需上架审核（免费版企业即可） | 企业内部应用，同左（个人免费「团队」亦可用 Stream） |

已排除项及原因：

- **企业微信**：回调与 H5 都强制公网 HTTPS，与「内网 Mac mini」决策冲突；且团队不在其上。
- **个人微信**：无审批/按钮交互开放 API；公众号 H5 路径受限且需企业主体认证，不投入。

推送目标从「群机器人 webhook」升级为「自建应用单聊推送审批人本人」（审批是点对点动作，不进群）；现有群机器人文本推送保留为降级路径。

## 5. 产品形态：三层模型

### A 层 · 卡片直审（本期核心，最短路径）

- 新期次周报计算完成后自动推送：高优结论逐条（或一张汇总卡）**交互卡片**——结论标题 + 关键数字 + 归因一句话 + 按钮【采纳】【驳回】。
- 回调 → 落库（复用行动状态机，幂等：先到先得，后到提示已处理）→ **更新卡片为结果态**（审批人 + 时间 + 结果）。
- **档 1 下卡片必须自解释**：无【详情】跳转（B 层不可用），卡片正文承载结论 summary 与关键证据数字；卡片备注输入列 M5（飞书/钉钉卡片表单可行）。
- 纯文本 digest 保留为降级（未配置自建应用时走现有群机器人路径）。

### B 层 · 移动 Web（IM 内 H5）——**推迟至档 2**

- 档 1 内网部署下，飞书/钉钉网页应用要求前端**公网 HTTPS 域名**，IM 内打不开内网页面 → 整层推迟。
- 档 1 期间的兜底：手机连办公室 WiFi 可开现有 PC 看板（局域网地址，无移动适配，仅应急核查）。
- 升级档 2（域名 + HTTPS + 内网穿透/云）后补做：`/m` 精简移动版（结论列表 / 证据核查 / 行动卡+备注）+ IM 免登。

### C 层 · 原生审批中心（M5+ 候选）

- 对接 IM 自带「审批」入口，审批进企业 OA 台账、走原生审批流（多人会签等）。两家流程模型差异大、模板维护成本高——除非有合规/台账硬诉求，不做。

## 6. 架构前提：档 1 · 内网 Mac mini 单实例（已决策）

**部署形态**：Mac mini 常驻运行服务（建议 launchd 开机自启 + 崩溃自动拉起），飞书长连接 / 钉钉 Stream 均为**服务主动外连公网 WebSocket**——零公网入站，无域名、无 HTTPS、无端口映射，维持内网安全边界。

网络与监听调整：

- 后端监听从 `127.0.0.1` 扩到**局域网地址**（MacBook/手机 WiFi 内可访问看板）；README 安全警告从「不要暴露公网」改写为「仅绑定可信局域网，不可端口映射到公网」。
- 已知取舍：局域网内写操作（PUT /api/actions）无鉴权——办公室可信内网下接受，与现状风险同级；升级档 2 时再引入会话鉴权。

单实例化的连带收益与代价：

- ✅ 解决 M3 已知限制「行动记录双机各自独立」：`actions.json` / 推送状态收敛到 Mac mini 单一事实源。
- ✅ MacBook 定位变为纯开发机：本地 `dev:all` 照常（本地数据/fixtures），生产数据只在 Mac mini。
- 代价：Mac mini 需常开；服务停机 = 推送与审批中断（launchd 拉起 + 健康检查缓解）。

数据与配置：

- 自建应用凭证（appId/appSecret、审批人 IM userid 映射）存 `data/im.json`，**不入库**（沿袭 notify.json 惯例）。
- `ActionRecord` 增加 `decidedBy` / `decidedAt` / `decidedVia`（card / pc），审批留痕。
- 并发：先到先得，后到回调返回「已被 XX 处理」结果态（对 IM 平台重试天然幂等）。

**档 2 升级路径（预留，不在本期）**：域名 + HTTPS 反代（或内网穿透）→ 解锁 B 层 H5 与 IM 免登 → API 会话鉴权。

## 7. 分期路线（定稿）

- **M4a · 内网单实例地基**：Mac mini 常驻部署（launchd）+ 后端监听局域网 + `ActionRecord` 审批留痕字段 + README 部署/安全/双机说明改写。
  验收：MacBook 浏览器访问 Mac mini 看板正常操作行动状态；Mac mini 重启后服务与数据自动恢复；旧 `PUT /api/actions` 行为不回归。
- **M4b · 飞书卡片直审**：飞书自建应用接入（长连接）→ digest 升级交互卡片（单聊推送审批人）→ 卡片回调验签 → 落库复用行动状态机 → 卡片结果态更新。
  验收：真实周报导入后 ≤1 分钟审批人手机收到卡片，30 秒内完成采纳；PC 看板状态同步一致；重复点击/平台重试不产生脏数据。
- **M4c · 钉钉卡片直审**：复用 IM 适配层，钉钉企业内部应用（Stream 模式）同能力；开工前先实测目标卡片类型的 Stream 回调支持（§8）。
  验收：同 M4b，且飞书/钉钉配置共存、按审批人配置分别推送。
- **M5+ 候选**（按需排期）：档 2 升级 + B 层移动 Web、卡片备注输入、多审批人（或签/会签）、超时未审提醒、C 层原生审批中心。

## 8. 风险与开放问题

- **钉钉 Stream 边界**：个别卡片交互场景要求 HTTP 回调模式（= 要公网）。M4c 开工前用目标卡片类型实测一次；若受限，备选方案为该场景仅飞书直审、钉钉走文本摘要+回到 PC（降级，不引公网）。
- **回调安全**：飞书/钉钉长连接模式下回调经由已建立的 WebSocket 通道，SDK 层完成校验；适配层仍按平台隔离测试、先校验后处理。
- **行动时效**：审批对象绑定期次；跨期未处理候选在 PC 看板可见，旧卡片仍可点但回调校验状态与期次后返回结果态。
- **常驻可靠性**：Mac mini 睡眠/断电 = 服务中断；launchd `KeepAlive` + caffeinate/节能设置项写入部署说明。
- **数据面演进**：多人写入后文件存储的并发瓶颈——先以「先到先得 + 原子写」锁住语义，SQLite 列 M5 候选（与「数据量增长后 DuckDB」候选合并评估）。

## 9. 决策记录

已决策（2026-09-27，用户确认）：

1. **平台范围 = 飞书 + 钉钉**；企业微信、个人微信（公众号/小程序）排除。
2. **部署 = 档 1 内网 Mac mini**：零公网入站，长连接/Stream 收回调；不购域名/云服务。
3. **B 层移动 Web 随档 1 推迟至档 2**（连带约束，见 §5）；本期卡片自解释，不做【详情】跳转。

默认假设（dev-flow ASSESS 阶段可推翻）：

- **首发平台 = 飞书**（M4b），钉钉随后（M4c）——飞书长连接卡片回调文档与 SDK 成熟度更稳；先后可换。
- **审批人 = 单人拍板**（沿用现有单决策人产品形态）；若实际多人，按「先到先得」语义天然兼容，或签/会签列 M5。
- 企业主体：飞书/钉钉自建应用免费企业即可创建，无认证门槛。
